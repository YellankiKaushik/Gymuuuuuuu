# Phase 20 personal-plan compatibility contract

The owner's Phase 20 request authorizes a six-exercise, twelve-muscle local pilot. It extends Phase 05's earlier predefined-program-only scope specifically for explicitly user-authored personal plans. Canonical programs and factual records remain unchanged.

Inspected the Phase 02/03 anatomy/exercise schemas and taxonomies, Phase 05 program/session/prescription contracts, Phase 06 workout/session/reference contracts, and Phase 17 typed-record/backup/restore/CSV contracts (including the original DOCX). Current implementation and later compatibility decisions govern physical storage.

Reuse `fitness-os-local` version 1, existing `records` store, module `plans`, with a new `personal-workout-plan` payload discriminator. No database/store migration or second backup format is needed. Record envelope schemaVersion 1; payload version 1; positive revision; stable personal plan/entry IDs; ISO created/updated instants; name; Session A and optional B; at most six unique allowlisted exercises per session. Sets/repetitions/rest are nullable. Limits are validation bounds, not recommendations. Rest stores integer seconds; explicit zero rest differs from null. Empty saved drafts are permitted; empty sessions cannot start workouts.

The generic record validator recognizes the discriminator or reserved personal-plan ID prefix, then validates the full strict plan contract. This covers the existing foundation backup and global Phase 17 restore preflight, including future versions and invalid ID relationships. Existing unrelated generic records remain compatible. Global portable backup already inventories `fitness-os-local.records` under its existing logical Phase 06 ownership. Workout-only module archives remain workout-only; the plan UI links to full backup and the existing CSV safety implementation. No formatVersion, registryVersion or normative historical schema is rewritten.

Atomic compare-and-swap checks the entire prior canonical JSON value inside the same IndexedDB transaction as update/delete, including record revision. Key order is normalized for restored JSON. Concurrent stale writes fail without overwriting records. Saves resolve only after transaction commit; the visible draft survives failures. Cross-tab change notices carry no personal payload; a dirty draft is never silently replaced.

Plan saves/deletions and workout creation reuse the data manager's existing restore-coordination lock: shared Web Locks for ordinary writes, exclusive ownership for restore. The established expiring localStorage lease is the fallback and contains only an operational owner/expiry, never personal records. A pending recovery journal blocks plan writes until recovery finishes. No second restore or coordination system is introduced. Tracker preferences are initialized through their existing owning API before a first plan workout, preserving complete-module backup compatibility.

Starting a plan session reuses existing `newSession`, `newSet` and `createWorkout`. It creates a normal personal/ad-hoc workout with canonical exercise IDs, copied display names and copied planned targets. Unspecified sets yield no pre-created sets; the person may add actual sets in the tracker. No load, repetition, schedule or clinical prescription is generated. The initial recording mode is repetitions-only and can be changed in the existing tracker. Personal provenance/revision is captured in existing notes/snapshot fields, not a false canonical program reference. Editing/deleting the plan cannot rewrite workout snapshots. Plan IDs/names are never added to shareable URLs or SSR; the existing generic return link opens the saved-plan workspace.

Use original code-native, approximate schematics grounded in the twelve records' existing location/actions and the six exercises' existing setup/execution/reset text. No inferred boundaries, activation, angles or human review. The six guides retain published difficulty (the one-arm row remains intermediate), equipment, sources, qualifiers and safety text. Record visual provenance and limitations separately from factual publication records.

Validation follows targeted contract/storage/portability/UI tests, then one final comprehensive gate. Production deployment requires subsequent owner approval of the exact verified commit.
